# PrintBench v0.11.0

PrintBench 0.11.0 reads sliced G-code files in full and shows each model's
plates side by side, with what each one prints with and whether it needs
someone at the printer partway through.

## Highlights

### Sliced plates

- **A plates table on the model page.** Every G-code file gets a row with its
  preview, print time, the filament in each slot, purge and tool swaps, layers
  and height, and the number of stops (filament changes and pauses), with
  when the first one comes. Printer, nozzle and object count sit under the
  name. The files are still listed in the file tree below.
- **A panel per plate.** Clicking a row opens everything else the file says:
  - the time split into printing and preparation, first-layer and silent-mode
    times
  - a filament table per slot with grams, length and purge, and how much of
    the filament is purged
  - a timeline of the print with a numbered marker for every stop and a tick
    in the new colour for every tool change, listed by time, layer and height
  - the print's footprint drawn on the bed, the objects on the plate, the main
    print settings, the machine and the slicer it was sliced with
  - Send, Open in slicer and Download beside the stop warning.
- **The slicer's own cost is not shown or stored.** It is priced with the
  slicer's per-kilo setting, not with this instance's pricing.

### Read once, in the background

- The worker reads each sliced file once, in full, when it is analysed, and
  stores what it finds. Pages, request forms and price estimates read that
  stored copy instead of opening the file again. Files the worker has not read
  yet are read on demand as before, so nothing changes until it gets to them.
- Choosing a plate in the request form no longer streams the whole file to find
  which tools it uses, and the "≈ €x to print" estimate no longer opens the
  file.

### Local quick start

- From upstream v0.7.6: each release now also publishes an nginx image and a
  versioned `compose.yaml` that starts a local instance with
  `docker compose up -d`. It generates and keeps the database password and auth
  secret on first startup. The file points at this fork's images.

## Upgrade notes

- **One database migration** adds three columns to `model_files`
  (`slicer_meta`, `slicer_meta_version`, `slicer_meta_error`). It runs
  automatically on startup and only adds nullable columns, so it is quick.
  Back up the database before upgrading, as for any release with a migration.
- **A one-off backfill follows.** Every 15 minutes the worker queues up to 500
  existing G-code files that have not been read yet, and reads each in full.
  Expect extra disk or S3 read traffic on large collections until it is through.
  Until a file has been read, its row says "Not read yet". A file that cannot be
  read is recorded and not retried until the reader changes.
- No environment changes and no backup-format change. Like thumbnails, the
  stored reads are derived from the files and are not part of the metadata
  backup; after a restore the worker reads the files again.
- For quick-start installs, back up the `credentials`, `pgdata` and `data`
  volumes together, and keep the credentials volume when recreating containers
  or replacing `compose.yaml`.
- If upgrading from an earlier version, also read the
  [v0.10.0 upgrade notes](v0.10.0.md) and the earlier release notes linked there.
